# Tutorial: Migrating to v1.13.0

This guide takes a node running any v1.12.x release to v1.13.0, and moves release tracking
to [`ethereumclassic/core-geth`](https://github.com/ethereumclassic/core-geth).

Budget about twenty minutes of downtime. **A resync is not part of this procedure** — your
chain data carries over.

## Why this migration

**This upgrade is pressing, and it is advised for every node still on a v1.12.x release.**

**The CVEs.** Six were reported against this client. The earliest v1.12.x releases carry all
six unpatched; later ones close some and not others. v1.13.0 carries every fix, plus a
GraphQL query depth limit. The [March 2026 audit](../audits/2026-03-security-audit.md) gives
the per-release breakdown, if you need to know what your current version is exposed to.

**The toolchain.** Every v1.12.x release is built on Go 1.21, which reached end of life in
August 2024. A node built from one inherits whatever has accumulated in the Go runtime and
standard library since, independent of anything in the client's own code. v1.13.0 builds on
Go 1.26.

**Where releases come from.** `ethereumclassic/core-geth` was created in December 2024 and is
where release work continues. A node tracking the previous repository will not see v1.13.0.

Two sections after the procedure carry the background.
[Why this release exists](#why-this-release-exists) covers the three audits and the
maintenance record of the v1.12.x line.
[What this client is for](#what-this-client-is-for-and-for-how-long) covers which networks are
maintained, and for how long.

## Before you start

Record what you are running, so you can tell afterwards whether anything changed that you
did not intend:

```bash
geth version
geth attach --exec 'eth.blockNumber'       <datadir>/geth.ipc
geth attach --exec 'net.peerCount'         <datadir>/geth.ipc
geth attach --exec 'admin.nodeInfo.enode'  <datadir>/geth.ipc
```

**Keep that last line.** It is your current enode ID, and step 3 changes it. An enode ID
cannot be re-derived once the key it came from is gone, so capture it now if you need it to
find the peer lists that reference this node.

### If you start the node without a network flag

**v1.13.0 runs Ethereum Classic when no network flag is given**, and `--mainnet` now means
the same as `--classic`. If your command line already names `--classic` or `--mordor`,
nothing in this section applies to you.

A v1.12.x node started without a flag was running Ethereum mainnet. If yours was, four
things change:

- **The data directory is Ethereum Classic's.** Without `--datadir`, the node uses the
  `classic` subdirectory of the default location, `~/.ethereum/classic` on Linux, which is
  the directory `--classic` has always used. Data in `~/.ethereum/geth` is left untouched
  and is not opened.
- **Accounts created without a flag are not found on their own.** Their keyfiles are in
  `~/.ethereum/keystore`, and they are not lost: pass `--keystore ~/.ethereum/keystore`, or
  copy the keyfiles into `~/.ethereum/classic/keystore`.
- **The cache allowance is `--classic`'s.** A bare start used to raise it to 4096 MB, as
  upstream does for Ethereum mainnet. Pass `--cache 4096` to keep that.
- **An explicit `--datadir` keeps the chain it holds.** A private network initialized with
  `geth init` keeps running from its stored genesis, and a data directory holding Ethereum
  Classic is kept on the current Ethereum Classic configuration, as `--classic` keeps it.

## 1. Stop the node cleanly

Stop it the way you started it.

**Docker:**

```bash
docker stop -t 300 core-geth
```

**`-t 300` is not optional.** `docker stop` sends SIGTERM, waits **10 seconds**, then SIGKILLs.
A clean shutdown writes cached state to disk first, which takes longer than that on a real
node — so a plain `docker stop` kills it mid-write, which is the one thing in this procedure
that costs you a resync.

**Binary in the foreground:** press Ctrl-C **once** and wait. A second Ctrl-C kills it.

**Binary under a service manager:** stop the service. This project has never shipped a systemd
unit, so the name is whichever one you wrote:

```bash
sudo systemctl stop core-geth
```

Either way, wait for this line before continuing:

```
INFO [..] Blockchain stopped
```

That line is the confirmation the database is consistent. If you do not see it, the node has
not finished writing — wait, do not proceed.

## 2. Install v1.13.0

Either take a release binary from
[`ethereumclassic/core-geth/releases`](https://github.com/ethereumclassic/core-geth/releases),
or build from source.

### Building from source

Build from the release branch, not from `main`. `main` continues to move, and a build from it
is not the release this guide describes:

```bash
git clone --branch archive-release-v1.13.0 --single-branch \
  https://github.com/ethereumclassic/core-geth.git
cd core-geth
make geth              # writes ./build/bin/geth
```

If that clone fails, v1.13.0 is not published yet — check the
[releases page](https://github.com/ethereumclassic/core-geth/releases).

**Do not clone with `--recursive`.** The three submodules hold consensus test fixtures, they
are several gigabytes, and `make geth` does not read them. They are needed only to run
the test suites.

Building needs Go 1.26. Confirm what you produced before installing it:

```bash
./build/bin/geth version
```

**The executable is still named `geth`, and nothing about how you invoke the client
changes.** Your systemd units, scripts and Docker commands keep working unaltered — this
release changes what the binary contains, not what it is called or where it reads from.

If you are replacing a binary in place, move the old one aside rather than overwriting it —
step 6 is easier with it still on disk.

**Docker users:** change the image reference to the one published from
`ethereumclassic/core-geth` and pull. Your volume mounts do not change. The node-key
rotation in step 3 still applies, and it operates on the mounted data directory.

## 3. Rotate the P2P node key

**This step is required.** CVE-2026-26315 is an oracle against the node key itself: an
invalid-curve ephemeral key in the RLPx handshake previously reached ECDH and failed only at
MAC verification, leaking key bits across repeated handshakes. A key used by an unpatched
node should be treated as exposed.

```bash
# node stopped
mv <datadir>/geth/nodekey <datadir>/geth/nodekey.old-rotated-$(date +%F)
```

Do not delete it — keeping it lets you prove which node an old enode ID belonged to. The
client writes a fresh key on the next start.

**Your enode ID changes.** Update every place that names this node:

- `static-nodes.json` and `trusted-nodes.json` on your own machines
- `StaticNodes` / `TrustedNodes` in any `config.toml`
- peer configuration held by anyone who peers with you deliberately
- monitoring, dashboards and allowlists that identify the node by enode

Read the new one after the node comes up, in step 5.

## 4. Re-check RPC exposure

The node is down, which makes this the cheap moment to check it.

- `--http.addr` should be `127.0.0.1` unless a trusted proxy terminates in front of it.
- `admin`, `debug` and `personal` do not belong in `--http.api` on any reachable interface.
- `--http.corsdomain="*"` allows any origin. Name the origins you actually need.
- The same applies to `--ws.addr` and `--ws.api`.

None of this is one of the six CVEs. It is the exposure that decides how much any future one
costs you.

## 5. Start, and verify

Start it the way you always do, with the new binary or the new image.

**Docker:** the image moves from `etclabscore/core-geth` to
`ghcr.io/ethereumclassic/core-geth`. Everything else about your invocation stays the same —
volumes, ports and flags do not change:

```bash
docker pull ghcr.io/ethereumclassic/core-geth:v1.13.0
docker rm core-geth
docker run -d --name core-geth \
  -v $LOCAL_DATADIR:/root \
  -p 30303:30303 -p 30303:30303/udp -p 127.0.0.1:8545:8545 \
  ghcr.io/ethereumclassic/core-geth:v1.13.0 \
  --classic --http --http.addr 0.0.0.0 --http.port 8545
```

**Both halves of that RPC exposure are deliberate.** `--http` alone binds the listener to
`localhost` *inside the container*, while Docker forwards a published port to the container's
external interface — so `-p 8545:8545` with the default address publishes a port that reaches
nothing, and the RPC appears dead with no error explaining why.

`--http.addr 0.0.0.0` binds every interface **inside the container's own network namespace**,
which is isolated; `-p 127.0.0.1:8545:8545` is what keeps it off the host's public interfaces.
**Publishing as `-p 8545:8545` with `0.0.0.0` instead exposes your RPC on every interface of
the host, which on a VPS is the open internet.**

If you do not need RPC from the host at all, drop both the `-p 127.0.0.1:8545:8545` and the
`--http*` flags.

**Binary:** run it as before, or start your service again.

Then four checks, in this order:

```bash
geth version                                                   # 1.13.0
geth attach --exec 'admin.nodeInfo.enode' <datadir>/geth.ipc   # new ID -> propagate it
geth attach --exec 'net.peerCount'        <datadir>/geth.ipc   # climbs within minutes
geth attach --exec 'eth.blockNumber'      <datadir>/geth.ipc   # resumes where it stopped
```

Under Docker, run those inside the container:

```bash
docker exec core-geth geth attach --exec 'net.peerCount' /root/.ethereum/classic/geth.ipc
```

**A peer count stuck at zero after ten minutes usually means step 3.** Peers that had you as a
static or trusted node still hold your old enode ID and cannot match the new one.

**Last, confirm you are on the network's chain.** Compare `eth.blockNumber` against a block
explorer or a second client; it should converge on the network head. If it settles somewhere
else, stop and investigate rather than resyncing — a divergence is worth reporting.

## 6. If you need to roll back

Your data directory is compatible in both directions, so rolling back is a swap of the binary
or the image tag.

**Docker:**

```bash
docker stop -t 300 core-geth
docker rm core-geth
# re-run your previous command, with etclabscore/core-geth:v1.12.x
```

**Binary:** stop the node, restore the binary you moved aside in step 2, start it again.

The rotated node key stays rotated, and should. Rolling back the client does not un-expose the
old key.

## What this migration does not require

- **No resync.** No finding in either audit corrupts chain data.
- **No new account keys.** These are network-layer and handshake issues; your keystore is not
  implicated. Rotate account keys only if `admin` or `personal` RPC was reachable from an
  untrusted network — that is its own exposure, not one of these CVEs.
- **No genesis or chain-configuration change.** ETC consensus rules are unchanged through
  Spiral, and v1.13.0 implements the same fork set as the release you are leaving.
- **No datadir change.** The instance directory stays `<datadir>/geth/` and the IPC socket
  stays `geth.ipc`. Both are set from constants in the client, not from the executable's
  name — renaming either is the one change that *would* force a resync, so do not.

## This procedure was executed before it was published

The claims above are measured, not inferred. The steps in this guide were run end to end
against a real Mordor data directory carrying a full chain, using the published `v1.12.23`
binary and a `v1.13.0` build:

| What was tested | Result |
|---|---|
| In-place upgrade, `v1.12.23` → `v1.13.0`, same datadir | Head preserved exactly; no resync |
| Rollback, `v1.13.0` datadir reopened by `v1.12.23` | Reopened cleanly; head preserved |
| Node-key rotation (step 3) | New key generated; chain data untouched |
| RPC exposure (step 4) | `--http` alone binds `127.0.0.1`; `--http.addr 0.0.0.0` binds all interfaces |

The rollback arm is the one worth calling out. It is the step most likely to be wrong and the
most damaging if it is, because it is the one an operator reaches for when something has
already gone badly — and nothing had previously tested whether the older client reopens a data
directory the newer one has written. It does, with the head intact.

This was run with peer discovery disabled, so any change in head across a restart would have
been the client rewinding rather than the network advancing.

## What this client is for, and for how long

**Core-Geth is maintained for Ethereum Classic and Mordor.** The other networks it
advertises fall into two different categories, and the difference matters before you point a
node at one.

**MintMe.com Coin is carried forward deliberately.** `--mintme` works in v1.13.0, and this
release includes the MintMe hardfork enabling PUSH0 and MCOPY. It is scheduled for deprecation
in a future release, and the reason it is here rather than already removed is to leave that
community a modernized client to build from — one on a supported Go toolchain with the CVEs
closed — instead of a fork of an abandoned one. Plan on that horizon, but v1.13.0 is a sound
base to start from.

**Ethereum and its testnets are not supported.** Support stops at Cancun and upstream has
since activated Fusaka, so this client cannot follow Ethereum mainnet, Sepolia or Holesky.
`--ethereum`, `--sepolia` and `--holesky` are deprecated and refuse to start. With no network
flag, or with `--mainnet`, the node runs Ethereum Classic.

**The v1.13 series is the last for Core-Geth.** It exists to close the security gap and carry
Ethereum Classic on a supported toolchain while the client is retired, not to begin a new line
of development. Plan on that horizon rather than on this release.

**On the wire this client speaks `eth/68`, and that is the version it will serve until it is
retired.** `eth/69` and later reach Ethereum Classic through
[Fukuii](https://fukuii.org) — developed at
[`fukuii-project/fukuii-cli`](https://github.com/fukuii-project/fukuii-cli) — and through the
Ethereum Classic extensions, overlays and plugins maintained against the mainstream Ethereum
clients. That combination is where client diversity comes from as this line ends, rather than
from any single implementation.

The Ethereum Classic core developers maintain reference clients and will continue to. **The
preferred client going forward is Fukuii, the only Ethereum Classic native client as of 2026.**
That succession is the normal shape of this ecosystem rather than a break in it:

| Client | Served ETC |
|---|---|
| Classic Geth | 2016–2018 |
| Parity | 2016–2020 |
| Multi-geth | 2018–2020 |
| Besu | 2020–2026 |
| Core-Geth | 2020–2027 |
| **Fukuii** | **2026–present** |

### Running Fukuii alongside during the transition

**The recommended path through 2027 is to run both, not to switch on a date.** Bring up a
Fukuii node beside your Core-Geth one, let them follow the chain in parallel, and compare
heads. When you are satisfied they agree, move your traffic across and retire the Core-Geth
node. Nothing forces a flag day, and running the two together is what tells you the cutover
is safe before you depend on it.

- **[fukuii.org](https://fukuii.org)** — the project, and where to start.
- **[`fukuii-project/fukuii-cli`](https://github.com/fukuii-project/fukuii-cli)** — the client
  itself, its releases and its documentation.

On one host the two contend for the same defaults, so give the second node its own datadir and
its own ports — P2P 30303, HTTP 8545 and WS 8546 are what both reach for. Two clients sharing
a datadir will corrupt it.

Nothing in this migration is affected by that horizon. v1.13.0 is the release to be on today:
supported for Ethereum Classic and Mordor through the sunset, and a modernized base for MintMe
until its own deprecation.

## Why this release exists

**The environment those releases now sit in.** The March 2026 attack went from a public
disclosure to a working exploit against production bootnodes quickly, and the tooling for
finding and weaponizing a disclosed flaw has continued to get cheaper and more automated since.
An unmaintained client is not merely behind in that environment; it is a standing, published
list of what to try. Closing the gap once is not sufficient — what a client needs is
development that is continuously reviewed, continuously tested, and instrumented well enough
that the next gap is visible while it is small. Rebuilding Core-Geth around that is as much a
part of v1.13.0 as the patches are.

Part of that rebuild is test coverage. Gaps in the existing consensus suites surfaced while
preparing this release, and
[`ethereumclassic/core-geth-tests`](https://github.com/ethereumclassic/core-geth-tests) is
being built to close them: a fixture corpus this project controls, rather than one it can only
read.

Three reports document the state of the v1.12.x line, all written before v1.13.0 was cut:

- [March 2026 security audit](../audits/2026-03-security-audit.md) — the six CVEs and the
  GraphQL denial of service, with the per-release breakdown.
- [August 2026 security follow-up](../audits/2026-08-security-followup.md) — v1.12.23,
  measured directly at the tag against the advisory records.
- [Dependency and toolchain modernization](../audits/2026-08-dependency-modernization.md) —
  what changed underneath the code between the December 2024 archive and this release.

Read together they describe a line that went **21 months without a substantive release** —
v1.12.20 in June 2024, then nothing until March 2026 — and was then patched under emergency
conditions during a live attack, with changes merged without a second reviewer.

**That last part is a security problem in its own right, separate from anything it fixed.** A
cryptographic patch that no one else reviews has no one positioned to catch a defect or a
malicious change shipped under cover of an urgency nobody wants to slow down. v1.13.0 and the
sunset period around it exist to close that condition, not only the vulnerabilities it
produced.
